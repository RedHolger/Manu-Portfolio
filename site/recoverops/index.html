RecoverOps

Accepts alert webhooks, proposes a policy-checked single remediation, executes it as a UID-pinned template-only patch in the lab, and verifies recovery from measured traffic before anything is called RESOLVED.

recorded live run Incidents, actions and events read straight out of the SQLite journal committed under results/recoverops/r3-live-20261003T151252Z/. Template bodies are replaced by their length; nothing else is edited.

State machine

RECEIVED → VALIDATING → OBSERVING → ELIGIBLE → EXECUTING → VERIFYING → RESOLVED
    ↘ OBSERVED (proposal recorded — observe mode)
any non-terminal → SUPPRESSED | CANCELLED
EXECUTING / VERIFYING → RECONCILING | ESCALATED
RESOLVED, ESCALATED, SUPPRESSED, CANCELLED are terminal: no outgoing edges.

Guardrails visible in this run

  • Two arms, one policy. The first incident stops at OBSERVED (observe mode, zero cluster writes); the second proceeds to PROPOSED and executes.
  • UID-pinned, template-only. The claim event records the target UID, resource-version and before/after hashes; replicas are not mutated.
  • Single action. One action row per incident; duplicates and re-deliveries are absorbed by the journal, not re-run.
  • Verification is separate from execution. A recovery is accepted only with three consecutive 10 s traffic windows (≥100 eligible, ≥99% success, ≥99% fast under 300 ms) inside a 180 s bound; missing telemetry escalates instead of retrying.
  • Limits re-checked at execution time: cooldown ≥600 s, ≤1 incident per incident, ≤3 per hour, allow-listed action only.

Status

Gates R1–R3 are ACCEPTED in RELEASE_STATUS.md. R4's corrected implementation (durable execution intents, UID-bound execution, autonomous verification) is implemented and offline-tested, not yet live-verified — this page shows the accepted R3 evidence only and makes no claim about R4.
