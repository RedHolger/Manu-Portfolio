The flywheel

One loop, three instruments. BudgetGuard observes — it scores measured telemetry against written SLOs and gates the release. FaultLab breaks — it injects bounded faults into an isolated lab to find where the SLO bends. RecoverOps heals — alert webhooks open incidents, policy picks one remediation, and measured traffic must prove recovery before anything is marked resolved. Everything below links to recorded evidence, never a live control plane.

BudgetGuard: SLO governance & deployment gating

Evaluates measured telemetry against written Service Level Objectives to control release velocity.

  • High-fidelity telemetry validation. Enforces a 20-second limit on consecutive source-sample timestamps (CheckCoverage), so release decisions rest on contiguous scrapes — a 30 s gap straddling the 15 s grid, or samples hugging opposite bucket edges, cannot hide inside occupied buckets.
  • Machine-readable release halt. Exit 0 PASS, 2 FAIL, 3 INCONCLUSIVE — designed to gate a pipeline; the halt itself is the caller's to wire, never a silent guess.
$ bin/budgetguard replay --fixture tests/fixtures/releases/error.json \
    --config configs/slos/reservations.yaml --end 2026-10-03T05:00:00Z --out /tmp/replay-error.json
decision: FAIL → /tmp/replay-error.json
$ echo $?
2
$ bin/budgetguard replay --fixture tests/fixtures/releases/healthy.json \
    --config configs/slos/reservations.yaml --end 2026-10-03T05:00:00Z --out /tmp/replay-healthy.json
decision: PASS → /tmp/replay-healthy.json
$ echo $?
0

FaultLab: proactive chaos engineering

Safely introduces turbulence into an isolated lab to validate resilience before customers are impacted.

  • Targeted disruption. Automated delay, connection failure, dependency outage and pod-reset scenarios with TTL-bounded faults and abort thresholds — every run journaled intent → apply → observe → cleanup → recovery health.
  • Deterministic execution. Per-phase workload evidence, bounded drain, and abort timing with headroom, so automated disruption and recovery sweeps cannot race the clock.

RecoverOps: automated remediation

Removes the human bottleneck from incident response with policy-driven safety nets.

  • Strict recovery gating. MaxRecoveryFailureRatio = 0.05 plus a hard floor of successful 2xx responses before anything is marked healthy — a quiet service is not a recovered one, and a permissive abort threshold can never leak into the verdict.
  • Rollback path. Severe degradation is restored from a known-good template via UID-pinned, template-only patches; the closed-loop SLI-triggered plane (R4) is implemented but unverified.

Status, honestly

The authoritative gate table lives in the repository (RELEASE_STATUS.md). Pages here never claim more than that table does: RecoverOps R4 and the full portfolio integration are implemented but not yet live-verified, and a short canary run never proves a 30-day SLO.

Safety

  • Static pages and JSON only. No authentication, no writes, no cluster access from the browser.
  • Fault injection, rollbacks and admin APIs are reachable only from a local, explicitly-named kind-sre-lab context.
  • The data files are generated by scripts/build-demo-site.sh from the Go CLI and committed results/ bundles; CI fails if they drift.
